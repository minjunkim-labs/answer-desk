# 0004. 품질 목표

- 상태: 제안
- 날짜: 2026-11-18

## 맥락

목표는 조건, 대상, 지표, 목표값으로 적는다. 지연은 평균이 아니라 p95·p99로 본다. 측정 환경은 노트북 한 대(Apple M4 Pro, 메모리 48GB)이고, 앱, PostgreSQL, 워커, k6를 모두 이 기기에서 돌린다. 이 환경의 수치는 서버 성능이 아니라 설계 비교의 근거로만 쓴다.

로컬 LLM 하나는 초당 수십 건의 답변을 만들지 못한다. 그래서 접수와 답변 완료의 목표를 나눈다.

## 결정

| 품질 특성 | 조건 | 대상 | 지표 | 목표값 |
| --- | --- | --- | --- | --- |
| 성능 | k6 50 RPS로 10분, 워커는 가짜 LLM | 접수 API | 응답 시간 p95 | < 200ms |
| 신뢰성 | 위와 같음 | 접수 API | 오류율(2xx가 아닌 응답과 시간 초과. 429 포함) | < 1% |
| 성능 | 동시 1~2건, 실제 로컬 LLM | 문의 접수부터 답변 또는 넘김 확정까지 | p95 | < 10초(잠정. 0003의 기준선을 잰 뒤 확정) |
| 신뢰성 | 처리 중인 워커를 강제 종료 | 접수된 문의 | 답변·넘김으로 끝나지 않은 건수 / 재처리 시작까지 걸린 시간 | 0건 / 60초 안 |
| 정확성 | 평가셋 전체, 확정한 기준값 | 내보낸 답변 | 틀린 답 비율 | ≤ 5% |

- 틀린 답: 넘기지 않고 내보낸 답변 중, 기대 근거와 다르거나 근거에 없는 내용을 말한 답변. 묵시적 오류(성공 응답인데 내용이 틀림)로 센다.
- 재처리는 0002의 처리 기한과 반복 작업으로 한다. Solid Queue만으로는 강제 종료된 작업을 다시 실행하지 않는다.

## 목표 없이 기록하는 지표

아래 지표는 재지만 아직 목표값이 없다. 목표값을 정하면 위 표로 옮긴다.

- 접수 API 응답 시간 p99: 위 성능 조건과 같은 측정에서 기록한다.
- 넘긴 비율: 정확성 조건과 같은 측정에서 기록한다. 틀린 답 비율과 맞바꾸는 값이라, 기준값을 고를 때 두 값을 함께 보고한다.

## 버린 대안

- 평균 지연을 목표로 두기: 느린 요청이 평균에 묻힌다. 지연은 p95·p99로 본다.
- 접수부터 답변까지 지연 목표 하나만 두기: 로컬 LLM 하나는 초당 수십 건의 답변을 만들지 못해, 접수 API의 성능을 LLM 속도와 나눠 볼 수 없다.
- 큐 작업 단위로 유실을 세기: 큐는 바꿀 수 있는 구현이다. 사용자에게 의미 있는 단위인 문의로 센다.

## 근거

- 접수 API는 저장과 큐 등록만 하므로 사용자가 기다리는 시간이 짧아야 한다. 200ms는 화면에서 바로 반응한다고 느끼는 범위로 잡았다.
- 답변 10초는 문의 창에서 "답변 중" 표시를 보며 기다릴 수 있는 시간으로 잡았다. 실제 로컬 LLM 속도를 재기 전이라 잠정값이다.
- 틀린 답 5%는 처음 목표다. 평가셋 규모가 작으면 1건 차이로 비율이 크게 흔들리므로, 평가셋 건수를 함께 적는다.

## 모니터링

- 4 Golden Signals를 본다. 트래픽(접수 RPS), 포화(큐 길이, 가장 오래 기다린 작업, DB 커넥션 풀), 지연(접수 p95·p99, 답변 완료 p95), 오류(2xx가 아닌 응답과 시간 초과, 429 포함. 틀린 답) 순서로 배치한다.
- k6 시나리오에 위 목표를 thresholds로 적어, 목표를 넘으면 실패로 끝나게 한다.

## 결과

- 측정할 때마다 기기, 데이터 크기, 동시성, 반복 횟수를 함께 기록한다.
- 목표값을 바꾸면 이 ADR을 고치지 않고 새 ADR로 바꾼 이유를 남긴다.
