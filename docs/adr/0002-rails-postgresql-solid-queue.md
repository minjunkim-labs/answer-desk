# 0002. Rails, PostgreSQL(pgvector), Solid Queue로 만든다

- 상태: 제안
- 날짜: 2026-11-18

## 맥락

이 서비스는 웹 애플리케이션이다. 운영자 콘솔(로그인, 넘겨받은 문의 목록, FAQ와 평가셋 관리)과 접수 API, 비동기 워커가 함께 있다. 기대 부하는 로컬 한 대에서 초당 수십 건의 접수다.

기술은 두 기준으로 고른다. 작성자가 처음부터 정한 방향(웹 애플리케이션은 Rails), 그리고 이 프로젝트에 맞고 일반적인 모범 사례인가.

## 결정

1. 웹 애플리케이션과 API는 Rails로 만든다.
2. 데이터와 벡터 검색은 PostgreSQL과 pgvector 하나로 한다.
3. 작업 큐는 Solid Queue(Rails 8 기본값)로 한다. 운영할 DB를 하나로 두려고 큐 테이블도 앱과 같은 PostgreSQL에 둔다(Solid Queue README의 "Single database configuration"). Solid Queue 설치 기본값은 큐 전용 DB다.
4. 문의가 유실되지 않는 근거는 큐가 아니라 문의 행의 상태다. 문의는 `received → processing → answered | handed_off` 상태, 처리 기한(`lease_expires_at`), 처리 차수(`attempt`)를 가진다. 끝나지 않은 상태(`received`, `processing`)의 행은 언제나 처리 기한을 가진다. 큐와 앱 데이터가 한 트랜잭션에 묶이는 동작에는 기대지 않는다. Solid Queue README가 이 동작에 기대는 설계를 경고하고, 큐를 다른 DB나 다른 백엔드로 옮기면 동작이 바뀌기 때문이다.
5. 접수 API는 문의를 `received`로, 처리 기한을 함께 넣어 저장하고 응답한다. 작업 등록은 `enqueue_after_transaction_commit`으로 저장이 커밋된 뒤에 한다. 커밋 뒤 작업 등록이 실패해도, 그 문의는 처리 기한이 지나면 7번의 반복 작업이 찾는다.
6. 워커는 문의를 `processing`으로 바꾸며 `attempt`를 1 올리고 새 처리 기한을 잡는다. 그 뒤 검색, 답변 생성, 근거 대조, 넘김 판정을 한다. 결과는 조건부 갱신 하나로 쓴다: 상태가 `processing`이고 `attempt`가 자기가 잡은 값과 같을 때만 쓴다. 갱신된 행이 0개면 결과를 버린다. 기한을 넘겨 늦게 끝난 워커가 재처리된 문의나 이미 넘긴 문의를 덮어쓰지 못하게 하기 위해서다.
7. 짧은 주기의 반복 작업(recurring task)이 `received`나 `processing` 상태로 처리 기한을 넘긴 문의를 찾아, 새 처리 기한을 잡고 다시 큐에 넣는다. 워커가 강제 종료되면 Solid Queue는 그 작업을 실패로 남기고 자동으로 다시 실행하지 않는다. 이 반복 작업이 그 빈틈을 메운다.
8. 재처리 횟수가 한도를 넘은 문의는 운영자에게 넘긴다.

## 버린 대안

- Rust(axum) API: 성능 이야기는 강하지만 운영자 콘솔을 따로 만들어야 한다. 이 부하에서는 Rails로 충분하다.
- Sidekiq + Redis: 빠르고 널리 쓰이지만 Redis를 하나 더 운영해야 한다.
- 큐와 앱 데이터의 한 트랜잭션에 기대기: 위 4번의 이유로 버린다.
- RabbitMQ, Kafka: 여러 서비스 사이에 메시지를 흘릴 때 맞다. 서비스 하나의 작업 큐로는 과하다.
- 별도 벡터 DB(Chroma 등): FAQ 규모에서는 pgvector로 충분하고, 저장소가 하나 줄어든다.

## 결과

- 운영할 저장소는 PostgreSQL 하나다.
- 큐 길이와 대기 시간을 DB에서 바로 볼 수 있다. 포화(Saturation) 지표로 쓴다(0004).
- 큐 처리량이 PostgreSQL 한계에 닿으면 큐를 바꾸는 결정을 새 ADR로 남긴다. 유실 방지는 문의 상태에 있으므로 큐를 바꿔도 이 보장은 그대로다.
- 다시 큐에 넣는 시각은 처리 기한과 반복 작업 주기의 합을 넘지 않는다. 재처리가 실제로 시작되기까지는 여기에 큐 대기 시간이 더해진다. 그래서 0004의 "60초 안 재처리 시작"을 지키려면 처리 기한, 반복 주기, 큐 대기의 합이 60초 안이어야 한다. 처리 기한과 반복 주기는 큐 대기를 잰 뒤 정하고, 목표는 강제 종료 시험으로 끝에서 끝까지 잰다.
